# 签名与发布

## 一、签名密钥

密钥只生成一次，之后所有版本都必须用同一份。换了密钥，已安装的用户无法覆盖升级，只能卸载重装。

JDK 21 自带 `keytool`，在仓库目录以外的安全位置执行：

```bash
keytool -genkeypair -v -keystore actionmental.jks -alias actionmental -keyalg RSA -keysize 4096 -validity 10950 -storetype PKCS12
```

PKCS12 格式下密钥口令恒等于库口令 —— `keytool -genkeypair` 会直接忽略 `-keypass`。
要让两者不同必须改用 `-storetype JKS` 并在生成后用 `keytool -keypasswd` 单独设置。

`.gitignore` 已挡掉整个 `.local/` 目录以及常见密钥文件。密钥离线备份到密码管理器或加密盘。

## 二、四个 GitHub Secret

仓库 Settings → Secrets and variables → Actions：

| Secret 名 | 取值 |
| --- | --- |
| `ANDROID_KEYSTORE_BASE64` | jks 的 base64 文本，**单行无换行** |
| `ANDROID_KEYSTORE_PASSWORD` | 库口令 |
| `ANDROID_KEY_PASSWORD` | 密钥口令，PKCS12 下与上一行相同 |
| `ANDROID_KEY_ALIAS` | `-alias` 的值 |

生成 base64：

```powershell
[Convert]::ToBase64String([IO.File]::ReadAllBytes("actionmental.jks")) | Set-Clipboard
```

```bash
base64 -w 0 actionmental.jks | tee actionmental.jks.base64
```

自查别名与口令：

```bash
keytool -list -v -keystore actionmental.jks -alias actionmental
```

## 三、本地出签名包

把本地签名材料集中放进项目的 `.local/signing/` 目录。该目录已被 Git 忽略：

```text
.local/signing/
├── actionmental-release.jks
└── keystore.properties
```

`.local/signing/keystore.properties` 内容如下：

```properties
storeFile=actionmental-release.jks
storePassword=你的口令
keyAlias=actionmental
keyPassword=你的口令
```

`storeFile` 必须指向**你自己那份 jks**，而且要和 `ANDROID_KEYSTORE_BASE64`
还原出来的是同一个。相对路径按 `.local/signing/` 解析，也可以填仓库外的绝对路径。

```bash
./gradlew :app:assembleRelease
```

没有这个文件时，`app/build.gradle.kts` 转而读 `ANDROID_KEYSTORE_PATH`、`ANDROID_KEYSTORE_PASSWORD`、
`ANDROID_KEY_ALIAS`、`ANDROID_KEY_PASSWORD` 四个环境变量 —— 这正是 CI 走的路径。
两者都没有时 release 包不签名（`signingConfig` 为 null），只能自己装来调试，不能分发。

## 四、发布流程

`.github/workflows/release.yml` 只有手动一个入口。Actions 页面运行 **Release (Manual)**，
选 `bump`（`patch` / `minor` / `major`），需要的话勾 `prerelease`。之后依次发生：

1. 读最新的 `v*` tag，按 `bump` 算出下一个版本号。没有 tag 时从 `v0.0.0` 起算。
2. 建**草稿** Release，Release Note 由 GitHub 自动生成。
3. 还原密钥 → 签名预检 → 跑单元测试与 lint → 构建签名 APK → `apksigner verify` →
   以 `actionmental_<版本号>_android_release.apk` 上传到草稿。
4. 确认草稿上确实挂着产物后，才正式发布。**git tag 在这一刻才被创建。**

不需要手工打 tag，也不需要手工填版本号。构建失败时草稿留在 Releases 页面且没有 tag，
删掉重跑即可，不污染 tag 序列。

只有 `versionName` 由 `-P` 传入，`versionCode` 在 `app/build.gradle.kts` 里从它推导：
`1.2.3` → `10203`（每段两位，MINOR 与 PATCH 不得超过 99，超了会串位，构建直接失败）。

版本号因此只有一个来源 —— tag。本地传同一个 `versionName` 就能得到同一个 `versionCode`，
两边的产物才有相同的版本标识并可用同一签名覆盖安装。早先 `versionCode` 用 workflow 的 `run_number`，
本地怎么传都对不上，同一份代码重跑一次 workflow 也会得到不同的号。
推导值仍然单调递增，降级保护还在，以后要上架商店也不用改。

`-PversionCode` 仍然认，是留给「设备上装着更高版本号又不想卸载」的逃生口。

四个 Secret 缺任何一个直接失败，不会退回未签名或 debug 签名。

## 五、签名预检

打包前先跑 `.github/scripts/SigningProbe.java`，用和 AGP 相同的 `KeyStore.getKey` 路径试开私钥。
没有它的话任何一种配错都只得到 packageRelease 阶段那句没有信息量的
`Failed to read key *** from store "...": null`。预检把它拆成三种能直接指认 Secret 的失败：

| 退出码 | 原因 | 怎么修 |
| --- | --- | --- |
| 10 | base64 不完整，或库口令不对 | 重新生成单行 base64；核对库口令 |
| 11 | `ANDROID_KEY_ALIAS` 写错 | 日志里会列出实际别名，照抄 |
| 12 | 两个口令都解不开私钥 | 本地 `keytool -list -v` 核对后重设 |

还有一种不算错的情况：`ANDROID_KEY_PASSWORD` 解不开、但库口令解得开。这是 PKCS12 的常态，
预检会打 warning 并改用库口令继续，不阻断发布。

`keytool` 自己测不出这件事：对 PKCS12，`-certreq` 和 `-importkeystore` 在 `-keypass` 不对时
会静默退回库口令并返回 0。这就是预检要用 Java 写而不是几行 keytool 的原因。

Secret 里的尾随换行和 CR 会被预检步骤剔掉 —— 粘贴时多带一个换行是最常见的坑。

## 六、debug 与 release 并存

| | applicationId | 应用名 | versionName |
| --- | --- | --- | --- |
| debug | `com.actionmental.debug` | Actionmental Debug | `0.1.0-debug` |
| release | `com.actionmental` | Actionmental | `0.1.0` |

同一台设备可以同时装两个，互不覆盖。

这个应用尤其需要区分：桌面图标、**无障碍服务列表**、**快捷设置磁贴**三处都按应用名列出。
所以 `app/src/debug/res/values/strings.xml` 除了 `app_name`，还覆盖了无障碍服务标签和两个磁贴名
（后缀 `(Debug)` / `(D)`），避免给错误的那一个开无障碍权限。

`ShizukuProvider` 的 authorities 是 `${applicationId}.shizuku`，天然随变体区分，不会冲突。
两个变体各自向 Shizuku 申请授权，互不影响。

## 七、本地部署到设备

### release：使用与 GitHub Release 相同的版本与签名

```powershell
./scripts/deploy-release.ps1
./scripts/deploy-release.ps1 -VersionName 1.2.0 -VersionCode 12 -Launch
./scripts/deploy-release.ps1 -VerifyOnly
```

前提是 `.local/signing/keystore.properties`（第三节）指向的 jks 与四个 Secret 里那份是同一个。
脚本逐步对齐 `release.yml` 的 build-android：同一条 `assembleRelease -PversionName`、
同一道 `apksigner verify --print-certs`，之后 `adb install --no-streaming -r` 并比对
设备上 base.apk 与本地 APK 的 SHA-256。

这证明设备上运行的是刚刚构建的本地 APK，并证明签名和版本配置与发布流程兼容。
脚本不会下载 GitHub Release 资产做哈希比较，因此不承诺本地 APK 与线上资产逐字节相同。

不传 `-VersionName` 时，版本号取**本地最新的 `v*` tag**（和 `release.yml` 的 create-release
同一条命令），没有 tag 才退回 `build.gradle.kts` 的默认值。工程默认值和线上没有任何关系，
拿它部署等于自造第三种版本；取 tag 才能直接对上 Release 页面上最新那份。
tag 落后于远端时先 `git fetch --tags`。HEAD 不在那个 tag 上时脚本会警告 ——
版本号说是 1.2.0、代码却是 tag 之后的 main，拿它当「线上那一版」排查会走岔。

没有签名材料时脚本**在构建之前**就失败。AGP 这时不会报错，只会出一个 `signingConfig` 为 null
的包 —— 它装得上、跑得起来，却和 Release 页面上的不是一回事，最容易被当成「和线上一样」用来排查。

两处和 debug 不同，都是 release 包不 debuggable 带来的：

- **不能降级安装**，但同号覆盖一直是允许的。同一个 `versionName` 反复部署得到同一个
  `versionCode`，所以每次都是同号覆盖，不用卸载也不会把设备顶到线上追不上的版本号。
  「装上去的确实是刚构建的那一份」不靠版本号证明，靠 SHA-256 比对。
  设备上装着更高版本号时（例如 `run_number` 时代留下的包），脚本会在跑 gradle 之前
  就报出来，并给出三条出路：换一个更新的 `-VersionName`、用 `-VersionCode` 顶上去、
  或者卸载重装（会清掉快捷键配置）。
- **签名必须一致**。指向了另一个 jks 就是 `INSTALL_FAILED_UPDATE_INCOMPATIBLE`，只能先卸载。

### debug

```powershell
./scripts/deploy-debug.ps1
./scripts/deploy-debug.ps1 -Device 192.168.1.5:5555 -Launch
./scripts/deploy-debug.ps1 -VerifyOnly
```

脚本沿用 Themental 那套命令：`adb devices` → `gradlew.bat :app:assembleDebug` →
`adb install --no-streaming -r -d` → 回读设备上 base.apk 的 SHA-256 与本地比对。

debug 的 versionCode 一律不动（默认 1）。早先这里会「现有版本 + 1」，结果是设备被顶到
只有本脚本才追得上的版本号，`./gradlew :app:installDebug` 再装就成了
`INSTALL_FAILED_VERSION_DOWNGRADE` —— 两条安装路径互相打架。
「装上去的确实是刚构建的那一份」改用比版本号更硬的证据：哈希。
`-d` 允许降级（只对 debuggable 包有效），这样从任何历史版本号都能装回来。

装完脚本会打出三项能力的真实状态（无障碍 / Shizuku / 实体键盘）。
无障碍没开时按键收不到，表现是「按了没反应」，很容易被当成代码 bug 排查半天，
所以脚本会直接给出开启命令：

```bash
adb shell settings put secure enabled_accessibility_services com.actionmental.debug/com.actionmental.service.KeyboardAccessibilityService
adb shell settings put secure accessibility_enabled 1
```
